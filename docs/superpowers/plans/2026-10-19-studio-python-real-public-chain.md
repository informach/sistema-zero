## Objetivo

Qualificar o caminho que a suíte controlada de 20 casos não exercita: login Auth, autorização Gateway/Members, POST de publicação no BFF, objetos no armazenamento S3 compatível, post no Hub PostgreSQL, página pública `/jogar/:id` sem cookie e remix adulto/Kids com cópia privada. Rodar com conta e banco descartáveis em loopback; nenhuma credencial de staging/produção.

## Topologia e fronteiras

- Reaproveitar a stack de QA `packages/members/tests/e2e/adult-parity-stack.mjs` (Auth, Gateway, Members, Hub) e ampliar só a fixture necessária a Estúdio Python. O script atual espera PostgreSQL isolado na porta 55433 e já possui conta adulta sintética e grants; não assume R2.
- Subir um serviço S3 compatível local pinado, dois buckets distintos público/privado e endpoint configurável no adaptador `member-shell/src/server/r2.ts`. O endpoint customizado é configuração de infraestrutura, ausente por padrão; no caminho normal continua a URL oficial R2. Rejeitar HTTP remoto, permitir HTTP apenas loopback. O SDK S3 real executa PUT/GET/DELETE e o teste confere bytes por SHA. O servidor Moto emula S3 por HTTP: prova integração do adaptador/SDK, mas não comportamento operacional do Cloudflare R2.
- Construir e servir Community e Kids em origens loopback descartáveis. O paridade atual remove todas as variáveis `R2_*` do processo antes de iniciar o Next standalone; criar um runner próprio da prova Python que passe só credenciais sintéticas locais, sem relaxar esse runner existente.
- A release Python usada por publicação/jogador deve ser a distribuição pinada D e o catálogo autorizado na stack; nenhum retorno forjado de `/api/studio/play`, `/api/studio/free-runtime` ou Hub.

## Casos de aceitação

1. Adulto autenticado cria/publica Python Classic+Turtle e Pro com idempotência; Hub SQL grava metadata de linguagem/runtime e playId; bucket privado guarda snapshot e bucket público guarda capa.
2. Browser anônimo abre `/jogar/:id`, executa Turtle com bitmap real; o mesmo URL mantém política de audiência. Jogo JavaScript existente continua abrindo na mesma página.
3. Remix adulto e Kids só importam após decisão de runtime para a própria audiência; cópia fica no namespace do usuário correto, autor original não muda. Revogação/sessão trocada cancela o import.
4. Ocultar/despublicar no Hub revoga a página pública e impede remix; objetos são limpos pelo fluxo assinado, sem apagar projeto privado do autor.
5. Provas negativas: runtime/release aposentada, extensão não concedida, playId de outra audiência, corpo de snapshot corrompido, armazenamento indisponível e requisição sem sessão. Cada falha preserva artefatos anteriores ou executa compensação documentada.

A falha incerta do Hub ganhou uma fila durável para capas candidatas. Antes de cada PUT público de capa, nas publicações de aula e avulsas, o BFF registra no bucket privado o `playId`, a chave, a URL original e o horário; isso inclui capas enviadas e capturas Pro. Kids e adulto têm prefixos e checkpoints distintos. Quando o Hub confirma a capa canônica, a intenção é reconhecida; no dedupe, a capa da tentativa extra é removida. Se a resposta do Hub se perde, a intenção permanece. Após uma hora o cron consulta o estado interno do post com audiência definida e compara a URL canônica: conserva a capa referenciada mesmo em post `hidden`, remove a tentativa divergente ou ligada a estado terminal/ausente e reconhece a intenção. Erro do Hub, contrato antigo ou falha de armazenamento conservam a intenção para novo processamento. A URL original registrada evita depender do domínio de mídia atual.

O endpoint `/hub/internal/studio-cover/:playId` expõe status e URL de capa apenas ao `member-shell` com HMAC no Gateway; a página pública de jogar não recebeu esse campo. O Hub passou a prova PostgreSQL/HTTP real; testes de reconciliação, cliente e publicação, typechecks e Biome passaram. O cron completo com Moto sob resposta perdida ainda precisa de prova.
